# Логика работы ChatKodi

## Короткая схема

Путь ответа теперь выглядит так:

```text
вопрос пользователя
  -> QueryIntentAnalyzer
  -> Retriever / EventStore
  -> EvidenceRecord
  -> фильтр по дате, объекту и типу вопроса
  -> дедупликация фактов
  -> статистика с явной единицей счёта
  -> StructuredAnswer
  -> GUI + кнопки источников
```

## Что делает каждый слой

`QueryIntentAnalyzer` определяет тип вопроса: один факт, список, статистика, период, подробный отчёт об активности, таймлайн и так далее. Также он выделяет даты, объект запроса и единицу счёта.

`Retriever` ищет фрагменты-кандидаты. Это ещё не ответ, а сырьё.

`EventStore` хранит предварительно извлечённые факты. Название историческое: в будущем его можно переименовать в `knowledge.db`, потому что модель уже уходит от узкого понятия события.

`EvidenceRecord` — текущая рабочая структура подтверждения. Она связывает найденный факт с исходным документом и текстовым фрагментом.

`StructuredAnswer` собирает ответ из подтверждённых записей. Для точных вопросов структурный ответ важнее LLM-пересказа, потому что LLM может красиво приклеить соседний мусор.

## Почему это важно

Старая ошибка выглядела так: программа находила дату, рядом находила слово про поражение, потом рядом находила другой результат и склеивала это как один ответ. Теперь точные вопросы должны проходить через строгую связку: объект + дата + действие + источник.
