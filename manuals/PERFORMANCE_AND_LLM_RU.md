# Производительность и локальная LLM

## Что изменилось в 1.8.0-rc5

В rc4 режим `Авто` мог выбрать самую крупную найденную LLM. На слабом CPU/low-RAM устройстве это приводило к очень долгой загрузке весов: программа уже нашла документы, но перед ответом начинала поднимать тяжёлую модель и зависала на `Loading checkpoint shards`.

В rc5 режим `Авто` стал безопаснее:

- RAG-вопрос сначала пытается дать структурный ответ по найденным данным.
- LLM не грузится заранее для каждого вопроса по документам.
- На CPU с малым объёмом RAM автоматический выбор пропускает тяжёлые 4B/7B модели.
- Ручной выбор модели в лаунчере по-прежнему разрешает запустить тяжёлую модель, если пользователь осознанно этого хочет.

## Почему 4B/7B на CPU может быть очень медленно

С версии 2.0 LLM — GGUF-файл Qwen3.5-4B Q4_K_M (2,7 ГБ) в llama.cpp. На видеокарте 8 ГБ модель целиком в видеопамяти (~68 токенов/с, загрузка 2–3 с). Без видеокарты модель работает на процессоре: нужно ~4 ГБ свободной ОЗУ, ответы заметно медленнее.

Для таких машин лучше использовать:

- `Qwen2.5-0.5B-Instruct` — самый лёгкий вариант;
- `Qwen2-1.5B-Instruct` или `Qwen2.5-1.5B-Instruct` — нормальный компромисс;
- режим `Только поиск`, если генерация не нужна.

## Что делать, если нужна LLM на слабом ПК

1. Откройте лаунчер.
2. Нажмите `Вернуть всё в Авто`.
3. Нажмите `Подготовить автоматически`.
4. Во вкладке `Модели` проверьте, что скачана лёгкая LLM.
5. Запустите ChatKodi.

Если вы вручную выбираете тяжёлую модель, ChatKodi будет уважать этот выбор, но запуск может быть очень долгим.

## Уточняющий вопрос по данным

Кнопка `Спросить по данным` не запускает новый поиск. Она отвечает только по тексту выбранного сообщения. Для красивого пересказа ей нужна локальная LLM, но в rc5 загрузка LLM не выполняется в GUI-потоке, поэтому интерфейс не должен зависать во время подготовки.

## Дополнение 1.8.0-rc6: почему стало быстрее

В rc6 исправлена важная ловушка lazy-режима. Раньше ленивый LLM-прокси мог отвечать интерфейсу «я доступен», хотя сама модель ещё не была загружена. Из-за этого RAG-запрос мог уйти в streaming-режим и внезапно начать грузить тяжёлую модель на CPU.

Теперь обычный вопрос по документам сначала проходит через поиск и структурный/direct answer. Если LLM ещё не загружена, интерфейс не запускает streaming заранее. Это особенно важно для машин с 8 GB RAM, где LLM на процессоре отвечает медленно.

Дополнительно:

- обновление streaming-текста стало чуть реже, чтобы меньше дёргать интерфейс;
- fade-анимации отключаются на очень слабом профиле;
- выбранная тема не влияет на производительность поиска и генерации.

# Оптимизация rc7

В rc7 автоподготовка стала осторожнее:

- Модели не скачиваются заново, если embeddings и LLM уже найдены.
- Для слабого CPU сохраняется fast-safe политика: ChatKodi не должен молча грузить тяжёлую 4B/7B модель в режиме Авто.

Если программа снова начинает долго висеть на `Loading checkpoint shards`, значит была вручную выбрана тяжёлая модель или включён профиль, разрешающий загрузку LLM на CPU. Для безопасного режима в лаунчере нажмите `Вернуть всё в Авто`.


## Важное правило rc8: слабый ПК не значит запрет LLM

В режиме **Авто** ChatKodi может не загружать тяжёлую модель на CPU/8 GB RAM, чтобы не подвесить интерфейс. Но если пользователь явно включил LLM в лаунчере или вручную выбрал модель, программа должна попытаться загрузить её.

Для этого во вкладке **Модели** есть галочка **«Разрешить LLM даже на слабом ПК»**. Она включает lazy-загрузку LLM и снимает запрет Memory Guard, но не расширяет контекст до опасных значений.
